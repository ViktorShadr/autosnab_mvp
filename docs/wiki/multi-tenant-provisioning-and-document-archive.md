# Multi-Tenant Table Provisioning and Document Archive

Три связанных, но разных вопроса, поднятых 2026-08-06 в переписке Виктора с Лилией (плюс два голосовых от бухгалтера Галины, переслала Лилия). Всё — идеи/вопросы без решения, код не менялся. Источники: `lilia_chat_multitenant_2026-08-06_1..4.png` (см. `manifests/raw_sources.csv`).

## 1. Как будет выглядеть таблица для новой организации (мультиарендность)

**Текущее состояние**: в боте прописан адрес одной конкретной Google-таблицы, бот пишет только в неё (см. `[[current-status]]`, `[[bot-backend-api-contract]]`). Схема на много организаций не реализована и не спроектирована.

**Вопрос Виктора**: то, что сейчас грузится ботом в таблицу Лилии — как это будет работать при масштабировании, если под каждую организацию нужна изначально пустая (чистая) таблица?

**Ответ и уточнения Лилии**:
- Таблица не должна быть полностью пустой — перед началом работы туда нужно загрузить справочник товаров от конкретного поставщика. Сейчас (для существующей таблицы) Марина вручную скопировала и вставила данные из Excel, предварительно почистив.
- Механизм настройки такой загрузки не определён — предположительно Марина в курсе. Скорее всего нужно в настройках бота прописывать, чтобы при загрузке данных о накладной данные справочника передавались тоже.
- Сопоставление справочника поставщиков договорились делать «на входе в УС» (учётную систему), но техническая реализация не ясна.
- **Одна таблица — на организацию, не на пользователя.** Причина: таблица хранит историю загрузок для сверки; при схеме «таблица на пользователя» усложняется учёт (сотрудники увольняются/приходят — придётся пересоздавать). Несколько пользователей заходят в одну Google-таблицу в режиме редактора одновременно, ограничений нет. При переходе MVP → сервис — обычная авторизация под разными пользователями.
- Организаций (клиентов бота) в перспективе может быть много — под каждую нужна отдельная таблица (это и был исходный вопрос Виктора, переформулированный после путаницы с «таблица на пользователя»).

**Предложенная (не решённая) схема**: одна эталонная «чистая» таблица с уже закреплёнными настройками бота (Лилия чистит копию, Виктор фиксирует настройки в ней) → при регистрации новой организации делается актуальная копия эталона.

**Открытая проблема без решения**: если после клонирования в эталонную таблицу вносятся правки (новые колонки, формулы, поведение), как автоматически докатить эти правки до уже существующих клонов, которые организации уже используют? Обсуждали «сделать обновление и загрузить» по аналогии с обновлением ПО, но конкретного механизма для Google Таблиц не нашли. Лилия прямо считает маловероятным, что штатные средства Google Sheets это поддерживают («было бы круто если б можно, но вероятно, что нет»).

**Статус**: открытый архитектурный вопрос, ничего не спроектировано технически. Кандидаты для будущего исследования: Google Sheets API (создание копии программно через `spreadsheets.copyTo`/`files.copy` реализуемо), но синхронизация схемы/формул в уже заполненные копии — отдельная нерешённая задача. Актуально к моменту перехода от MVP («одна организация — Кафе Ромашка») к сервису на несколько клиентов.

## 2. Сворачивание истории загруженных накладных (Галина, бухгалтер)

Переслано Лилией как голосовое сообщение от бухгалтера Галины (~01:02).

**Жалоба**: таблица растёт сверху вниз с каждой загрузкой (на момент сообщения — уже 303-я строка). При открытии таблица показывает нижнюю/текущую видимую часть, и чтобы попасть к недавно загруженным документам, нужно каждый раз прокручивать. При большом объёме это неудобно — хочется быстро загрузить пачку документов, сверить и не листать вниз, путаясь среди старых записей.

**Запрос**: возможность сворачивать уже загруженные накладные, например по периодам (по месяцу) — «архивировать» старые блоки, оставляя видимой только текущую/недавнюю работу.

**Связь с уже открытым пунктом**: это конкретное, живое подтверждение уже зафиксированного пункта UX-хардининга бота — сворачиваемые строки по документам, см. `[[telegram-bot-ux-hardening-plan]]` (раздел про UI-пожелания Лилии, 2026-07-31: «collapsible rows per document»). Ранее это было абстрактным пожеланием Лилии; теперь есть прямая формулировка от конечного пользователя-бухгалтера с конкретным сценарием (307+ строк, сортировка по периодам).

**Статус**: идея, не реализовано, не заскоуплено технически (Google Sheets поддерживает группировку строк (`Group rows`) — вероятный кандидат-механизм, не проверялся).

## 3. Электронный архив исходных документов (Галина, бухгалтер) — новое требование

Переслано Лилией как второе голосовое от Галины (~00:30) + пояснение зачем (~00:30).

**Запрос**: помимо табличных данных, нужен архив самих исходных файлов (фото/PDF накладных и чеков), которые проходят через бота — организованный по периодам. Пример сценария Галины: за июль 2026 загружено ~100 накладных; хочется, чтобы в облаке (сервер/Google Drive/диск) сформировалась структура папок по месяцу и внутри — по дате загрузки (например «1 июля — 5 накладных», «10 июля — N накладных» и т.д.).

**Зачем** (её же формулировка): при возникновении разногласий с поставщиком быстро найти исходный документ за нужную дату, не копаясь в переписке/чатах — открыть архив, перейти к периоду, найти файл.

**Реакция Виктора (переслано Лилии, ещё не финализирован ответ)**: считает задачу реально выполнимой технически, отмечает что для объёма хранения потребуется платная подписка (Google Drive/облако).

**Текущее состояние в коде**: загруженные файлы сохраняются локально на бэкенде (`backend/uploads`/`exports` — см. существующий деплой на VPS и `auto-snab-document-parser`), но нет структурированного, доступного пользователю облачного архива с навигацией по датам. Это отдельная задача от уже существующего локального хранения загрузок на диске контейнера.

**Статус**: новое требование, не в объёме `[[telegram-bot-ux-hardening-plan]]` и не в других существующих планах. Нужно решить: (1) куда складывать — Google Drive (та же организация, что и таблица) или отдельное S3-совместимое хранилище (сравнимо с уже обсуждавшимся Yandex Object Storage в контексте СБИС, см. `[[sbis-edo-integration]]`); (2) структура папок (по организации → году → месяцу → дню, как предложила Галина); (3) кто оплачивает подписку/хранилище. Ответ пользователя Лилии пока не дан.

## Следующие шаги (не решено, кто и когда)

1. Мультиарендность: спроектировать схему провижининга Google-таблиц под организации, включая (нерешённый) вопрос синхронизации будущих правок эталона в уже созданные копии. Актуально не прямо сейчас (MVP — одна организация), но встанет при масштабировании.
2. Сворачивание строк по периодам — можно объединить с уже запланированным пунктом сворачиваемых строк в `[[telegram-bot-ux-hardening-plan]]`, оценить `Group rows` в Google Sheets API.
3. Электронный архив документов — требует отдельного решения по хранилищу и оценки стоимости подписки, прежде чем проектировать. Виктору нужно дать окончательный ответ Лилии/Галине.
