# Telegram Bot UX Hardening Plan

Полное техническое задание на доработку Telegram-бота «АвтоСнаб MVP Парсер», полученное от пользователя 2026-08-05. Ничего из этого ещё не реализовано — это план на день/итерацию, зафиксированный до начала работы.

## 1. Цель доработки

Повысить понятность и надёжность взаимодействия пользователя с ботом при загрузке и обработке накладных: убрать технические детали из пользовательских сообщений, сделать процесс проверки данных интерактивным прямо в чате, а также улучшить онбординг новых пользователей.

## 2. Обработка и маскирование ошибок (приоритет 1)

**Текущее поведение**: в чат пользователю попадают сырые исключения внешних сервисов, например «OpenAI invoice parsing failed: Error code: 403 - unsupported_country_region_territory» или «Google OAuth token устарел или отозван. Откройте /api/v1/google-oauth/authorize и выполните вход заново».

**Требуется**:
- Слой перехвата ошибок между внешними интеграциями (OpenAI, Google Sheets/OAuth) и модулем отправки сообщений в Telegram.
- Пользователю — дружелюбное сообщение общего вида («Не получилось обработать документ, мы уже разбираемся, попробуйте прислать фото ещё раз через пару минут») без кодов ошибок, стектрейсов и внутренних путей API.
- Отдельный канал уведомления администратора/техподдержки (лог, отдельный чат или алерт в мониторинге) с полным текстом ошибки для диагностики.
- Критически важные инфраструктурные сбои (например протухший Google OAuth токен) не должны требовать действий от конечного пользователя — это ответственность администратора, и такие сообщения должны попадать только в служебный канал.

**Критерий приёмки**: ни одно сообщение пользователю не содержит англоязычные коды ошибок, JSON, названия внешних API или служебные url-эндпоинты.

## 3. Сокращение количества служебных сообщений (приоритет 4)

**Текущее поведение**: на одно загруженное фото формируется от трёх до пяти последовательных сообщений («Страница 1 добавлена» → «Обрабатываем через ИИ…» → «Загружаем в таблицу…» → итоговая карточка), засоряя ленту чата.

**Требуется**: переход на редактирование одного сообщения по мере смены статуса обработки через `editMessageText` вместо отправки новых сообщений на каждом шаге, либо (если технически ограничено, например из-за смены типа контента) сокращение числа промежуточных статусов до одного объединённого.

**Критерий приёмки**: на одну загруженную страницу документа в чате остаётся не более одного-двух сообщений от бота после завершения обработки.

## 4. Интерактивная проверка данных через inline-кнопки (приоритет 2)

**Текущее поведение**: сообщения «документ обработан, но требует проверки» и «документ похож на уже загруженный (дубль)» не дают пользователю действия внутри Telegram — только ссылка «Открыть таблицу» во внешний Google Sheet.

**Требуется**:
- Inline-кнопки под карточкой с распознанными данными: подтверждение записи как верной; пометка «это дубликат — пропустить» или «не дубликат — добавить»; запрос исправления конкретного поля (поставщик, номер, дата, сумма) через диалог, где пользователь присылает новое значение в ответ.
- Публикация в таблицу для документов «требует проверки» — только после подтверждения пользователем, не автоматически.

**Критерий приёмки**: пользователь может подтвердить, отклонить или скорректировать распознанные данные, не покидая Telegram.

## 5. Прозрачность качества распознавания (приоритет 5)

**Текущее поведение**: в части карточек присутствуют все четыре поля (поставщик, номер, дата, сумма), в других — только сумма без объяснения причины; встречаются подозрительные даты, не соответствующие ожидаемому году.

**Требуется**: модуль распознавания возвращает уровень уверенности по каждому полю; если поле не распознано или уверенность ниже порога, бот явно указывает это в карточке («дата: не распознана» или «сумма: 12840.0, требует проверки — низкая уверенность») вместо тихого пропуска или показа сырых данных без оговорок.

**Критерий приёмки**: пользователь всегда видит все четыре поля в карточке результата, сомнительные значения визуально помечены.

## 6. Онбординг и справка (приоритет 3)

**Текущее поведение**: профиль бота не содержит описания (bio); из команд доступны только `/done`, `/status`, `/reset` — нет `/start` и `/help`.

**Требуется**:
- `/start` с приветственным сообщением, кратко описывающим сценарий работы (пришлите фото страницы документа, при необходимости пришлите ещё страницы, затем `/done` для завершения).
- `/help` с перечнем всех доступных команд и их назначения.
- Заполненное описание бота в BotFather (about/description).

**Критерий приёмки**: пользователь, впервые открывший чат с ботом, получает инструкцию по началу работы без обращения к третьим лицам.

## 7. Тон сообщений (приоритет 6, последний)

**Текущее поведение**: часть служебных ответов звучит резко для отказа («Активного черновика нет», «Сначала пришлите хотя бы одну страницу документа»).

**Требуется**: смягчить формулировки, сделать более конкретными с точки зрения следующего действия — заменить отказ на подсказку с примером нужного действия.

**Критерий приёмки**: ни одно сообщение об отсутствии данных или невозможности выполнить команду не заканчивается без указания, что нужно сделать пользователю дальше.

## 8. Приоритизация (порядок реализации)

1. **П.2 — маскирование ошибок** (наиболее критично для доверия пользователей и безопасности данных)
2. **П.4 — интерактивная проверка данных через inline-кнопки**
3. **П.6 — онбординг и справка**
4. **П.3 — сокращение служебных сообщений**
5. **П.5 — прозрачность качества распознавания**
6. **П.7 — тон сообщений**

## Статус

План зафиксирован 2026-08-05, реализация не начата. Целевой репозиторий для реализации (`autosnab_mvp` и/или `auto-snab-document-parser`) не уточнён пользователем — оба репо параллельно поддерживают этот Telegram-бот (см. `[[auto-snab-document-parser-release-repo]]`), уточнить перед началом кода.
