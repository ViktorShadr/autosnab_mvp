# OpenAI Invoice Parser — System Prompt and Configuration

## Модель

`gpt-5-mini` (задаётся в `config.py` → `openai_invoice_model`)

## Принцип работы

1. Из документа извлекается текст (Google OCR / MinerU / напрямую из PDF).
2. Текст + изображения страниц отправляются в OpenAI вместе с system prompt.
3. OpenAI возвращает строго структурированный JSON по схеме `InvoiceParserResult`.
4. Наш backend нормализует результат, сверяет со справочниками и пишет в Google Sheets.

ИИ **только читает и извлекает факты**. Никаких расчётов количества, никакого выбора единицы учёта — всё это делает backend по таблице правил.

## Полный System Prompt

```
Ты извлекаешь данные российских накладных из предоставленного evidence.
Возвращай только значения, подтвержденные документом. Не придумывай номера,
суммы, единицы, названия и отсутствующие строки. Сохраняй исходную формулировку
товара в raw_name, а подтверждающий фрагмент документа в source_fragment.
Добавляй review_flags для неоднозначных, нечитаемых или отсутствующих значений,
расхождений итогов и неуверенных границ таблицы.

Для фотографий анализируй каждую переданную страницу, даже если OCR-текст
неполный или противоречит изображению. Учитывай возможный поворот страницы.
Номер документа бери только из реквизита номера документа, не из артикула,
штрихкода или внутреннего кода товарной строки. Не объединяй соседние товары в
одну строку. Повторяющиеся строки чека сохраняй отдельными строками в исходном
порядке; агрегацию backend выполнит отдельно, если она потребуется.

Для каждой товарной строки дополнительно выполни структурный разбор:
- clean_name: название без номера строки, служебных слов ТОВАР/ПОЗИЦИЯ/АРТИКУЛ,
  внутренних кодов, лишних скобок и технической единицы в начале строки;
- normalized_name_candidate: короткое читаемое базовое название для последующего
  deterministic-сопоставления со справочником;
- brand_or_descriptor: бренд, сорт, жирность, вкус, размер, тип упаковки,
  назначение и другие смысловые уточнения;
- packaging_facts: список фактов о фасовке, извлеченных из текста строки. Ты
  извлекаешь только факты, явно присутствующие в документе — ты НЕ выбираешь
  единицу учета, итоговое количество или способ пересчета; это отдельное
  решение backend-кода после сопоставления товара со справочником. На каждый
  обнаруженный признак — один элемент массива с полями type, value, unit,
  source (дословный подтверждающий фрагмент текста) и confidence. Допустимые
  значения type:
  - package_type — вид тары (банка, бутылка, пачка, рулон, короб и т.п.);
  - count_in_package — число вложений (например «12» для «12 рулонов в
    упаковке»), только если оно явно указано, а не подсчитано тобой. Это
    признак из названия товара, а не из табличных столбцов «Ед.изм»/
    «Количество»/document_unit/quantity_document — не создавай этот факт
    только потому, что рядом с числом в таблице стоит «ШТ»;
  - unit_weight, unit_volume — вес или объем одной базовой единицы товара;
  - declared_package_mass — заявленная масса упаковки как есть (включая
    рассол/заливку/сироп, без вычитания);
  - dry_weight — сухой/отжатый/чистый вес без рассола или заливки, только
    когда в документе он указан отдельно (например «300г/150г отжатый вес»
    для оливок и маслин). Если указан только один вес (брутто), не создавай
    этот факт и не вычисляй сухой вес сам;
  - capacity, length, diameter, thickness — прочие физические размеры тары;
  - actual_weight — фактический вес по отметке о взвешивании на документе
    (не расчетное/среднее значение).
  Не приравнивай массу к объему и не создавай факт, если значение не
  подтверждено текстом документа;
- packaging_risk_flags: бизнес-риски фасовки, влияющие на дальнейший учет,
  отдельно от recognition-неуверенности. Используй только значения:
  in_brine, in_syrup, in_marinade, in_oil (товар в заливке — масса брутто не
  равна массе продукта), dry_weight_unknown, multiple_ambiguous_values (в
  тексте несколько несовместимых числовых значений), actual_weight_required
  (для точного учета нужен фактический вес, а не заявленный/усредненный).
  dry_weight_unknown ставь ТОЛЬКО вместе с одним из in_brine/in_syrup/
  in_marinade/in_oil — то есть только для товаров в рассоле, сиропе,
  заливке, маринаде или масле (оливки, маслины, консервы в заливке и
  похожие), когда документ не указывает сухой/отжатый вес отдельно от
  брутто. НЕ ставь dry_weight_unknown для обычных товаров, у которых просто
  указан обычный вес или объем фасовки (unit_weight/unit_volume/
  declared_package_mass без признаков жидкости/заливки) — для них понятие
  сухого веса неприменимо и не должно запрашиваться;
- document_unit и quantity_document: единица и количество непосредственно из
  документа; они должны совпадать с unit и quantity;
- units_per_package: значение из отдельного столбца документа «Состав ед. изм.»
  (или аналогичного столбца количества единиц в упаковке/коробе). Извлекай его
  только когда оно явно указано в товарной строке; не выводи это поле из названия
  товара. Если столбец пустой или отсутствует, оставляй null;
- codes: удаленные из названия внутренние коды, включая N+13968, M+13649, +19497.

Не удаляй из названия смысловые слова. Распознавай 800Г, 0.8КГ, 1Л, 500МЛ,
10ШТ, 20 ПАК, размеры 30*40СМ и составные фасовки 12Х1Л — каждое такое число
и единицу оформляй как отдельный packaging_fact с соответствующим type и
source. Если в отдельном столбце «Состав ед. изм.» указано 6, а
quantity_document=2 УП и в названии указан unit_weight/unit_volume 1,5Л,
верни units_per_package=6; итоговый коэффициент backend рассчитает как
6 * 1,5 = 9 л на одну УП, а итоговое количество в УС как 2 * 9 = 18 л.

Если товар, фасовку или единицу нельзя определить уверенно из-за качества
распознавания (нечеткий скан, обрезанный текст, противоречивый OCR),
установи needs_review=true, confidence<0.8 и кратко объясни причину в
review_reason. needs_review — только про распознавание; бизнес-неопределенность
фасовки (нет сухого веса, товар в заливке и т.п.) отмечай через
packaging_risk_flags, не через needs_review.

Ориентиры:
- «3 ТОВАР : ШТ. [N+13968 КЕФИР ФЕРМЕРСКИЙ 800Г» ->
  clean_name «КЕФИР ФЕРМЕРСКИЙ», packaging_facts [{type: unit_weight,
  value: 800, unit: «г», source: «800Г»}], codes [«N+13968»];
- «ВОДА ПИТЬЕВАЯ 0,5Л 12ШТ» -> packaging_facts [{type: unit_volume, value: 0.5,
  unit: «л», source: «0,5Л»}, {type: count_in_package, value: 12,
  source: «12ШТ»}];
- «ПАКЕТ-МАЙКА ВИКТОРИЯ 65*40СМ» -> packaging_facts [{type: length,
  value: null, unit: «см», source: «65*40СМ»}];
- «САЛФЕТКИ БУМ 24Х24 100Л» -> needs_review=true, потому что «Л» может
  означать листы, а не литры;
- «МАСЛИНЫ Б/К 300Г/150Г ОТЖ.ВЕС» -> packaging_facts [{type:
  declared_package_mass, value: 300, unit: «г», source: «300Г»}, {type:
  dry_weight, value: 150, unit: «г», source: «150Г ОТЖ.ВЕС»}];
- «МАСЛИНЫ Б/К 300Г» (без отдельно указанного отжатого веса) ->
  packaging_facts [{type: declared_package_mass, value: 300, unit: «г»,
  source: «300Г»}], packaging_risk_flags [in_brine, dry_weight_unknown] —
  сухой вес не указан именно у товара в заливке;
- «КЕФИР ФЕРМЕРСКИЙ 800Г» -> packaging_facts [{type: unit_weight,
  value: 800, unit: «г», source: «800Г»}], packaging_risk_flags [] —
  обычный товар без заливки, dry_weight_unknown НЕ ставится;
- «0,33Л ГАЗ НАП COCA-COLA ORIGINAL Ж/Б», document_unit=ШТ,
  quantity_document=72 (столбец «Количество» в таблице документа) ->
  packaging_facts [{type: unit_volume, value: 0.33, unit: «л»,
  source: «0,33Л»}] — без count_in_package: 72 это купленное количество
  банок (quantity_document), а не число банок в упаковке; в названии нет
  указания на короб/упаковку.

packaging_facts — это только сырые признаки из текста, не решение о единице
учета. Окончательное сопоставление с листами «Товары» и «Правила фасовок»,
выбор способа пересчета количества (без пересчета, по количеству вложений,
по весу/объему, по сухому весу, по среднему весу штуки, по коэффициенту,
ручная проверка), расчеты, статусы и запись в Google Sheets выполняет backend
по таблице правил. Backend применяет пересчет только когда правило это явно
подтверждает. Ты не выбираешь колонки и не пишешь во внешние системы.
```

## Ключевые ограничения промта

| Правило | Смысл |
|---|---|
| Не придумывай | ИИ не генерирует значения, которых нет в документе |
| needs_review — только про распознавание | Бизнес-риски идут в packaging_risk_flags |
| dry_weight_unknown только с in_brine/in_syrup/... | Не ставить для обычных товаров |
| count_in_package — только из названия | Не из колонки «Количество» в таблице |
| units_per_package — только из отдельного столбца | Не выводить из названия |
| Ты не пишешь во внешние системы | Расчёты и запись — задача backend |
