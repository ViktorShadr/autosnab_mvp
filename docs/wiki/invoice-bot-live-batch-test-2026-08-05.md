# Live batch test — 24 real накладные через Telegram-бота + Langfuse (2026-08-05)

## Идея и цель

Пользователь предложил прогнать пачку реальных накладных (фото из `~/Загрузки/Накладные`, 29 файлов) через живого Telegram-бота `@autosnab_parser_test_bot`, параллельно наблюдая за Langfuse-трейсами и результатом в Google Sheets, чтобы получить статистику для решений по доработке кода. Ассистент управлял браузером (Telegram Web + Langfuse Cloud + Google Sheets) напрямую, без участия пользователя в самой загрузке.

Бот на момент теста работал в **GitLab dev-окружении** (`auto-snab-document-parser`, контейнер `auto-snab-docparser` на dev-хосте), не на VPS `78.17.160.248` — пользователь явно поправил ассистента в процессе, когда тот по умолчанию начал диагностировать не тот хост.

## Подготовка входных данных

- 29 файлов в исходной папке. Дедупликация по MD5 показала 3 пары/тройки байт-в-байт идентичных файлов (случайно сохранённые дубликаты, не страницы) → 25 уникальных изображений.
- Один явный случай многостраничного документа по имени файла: `459 с1` / `459 с2` (страница 1 / страница 2 одной накладной №459).
- Остальные группировки страниц проверялись через контактный лист (Python/Pillow, сетка миниатюр с подписями) — визуально подтверждено, что все остальные уникальные изображения являются самостоятельными завершёнными документами (шапка + таблица + подписи в одном кадре), а не частями другого файла.
- Итог: **24 накладные** (23 одностраничных + 1 двухстраничная из пары `459 с1`/`с2`).

## Механика загрузки через Telegram Web (для будущих прогонов)

- Файл прикрепляется через меню paperclip → «Document» (не «Photo or Video» — сохраняет исходные байты без телеграмного пережатия).
- Каждая страница подтверждается ботом сообщением «Страница N добавлена.» с инлайн-кнопками «✅ Готово» / «🗑 Сбросить».
- **`/done` как текстовая команда не финализирует черновик** — сообщение отправляется, но бот его никак не обрабатывает (ни ответа, ни ошибки), черновик просто продолжает копить страницы. Только клик по инлайн-кнопке «✅ Готово» реально запускает `finalize_draft`. Это расходится с текстом самого бота («…нажмите «✅ Готово» под сообщением или отправьте /done») и с `docs/wiki/telegram-bot-ux-hardening-plan.md`, где `/done` перечислен как существующая команда.
- Кнопка «Готово» **не всегда** реагирует на первый клик — координаты сдвигаются по мере роста истории чата, а также сама вкладка Telegram Web периодически показывала оверлей "App is inactive... Another app is running" (конфликт с другой открытой сессией Telegram Web) — оба эффекта вместе несколько раз приводили к тому, что следующая отправленная страница приклеивалась вторым/третьим листом к незакрытому черновику предыдущей накладной. Каждый раз чинилось через `/status` (проверить реальное число страниц) → «🗑 Сбросить» → пересылка файлов заново.

## Ход прогона и сбой инфраструктуры

Первые 18 накладных обработались штатно (22:16–23:11). Затем очередная загрузка (накладная a4b8fe44) вернула прямо в чат сырой traceback:

```
(psycopg2.OperationalError) could not translate host name
"c-c9q76fhi8q5o8e3hj2he.rw.mdb.yandexcloud.net" to address:
Temporary failure in name resolution
```

DNS-резолвинг managed PostgreSQL (Yandex Cloud) отвалился на dev-хосте. После этого бот на ~5 минут вообще перестал отвечать даже на `/status`. Кратковременно ожил (обработал ещё 2 накладные — №20, №21), затем снова замолчал и уже не восстановился до конца сессии — ни на новую накладную, ни на `/status` за 15+ минут.

**Диагностика (read-only, без вмешательства в прод):**
- SSH-доступа к dev-хосту `auto-snab-document-parser` нет (в отличие от `autosnab_mvp`'s собственного VPS) — только Docker-сокет, примонтированный в `dev`-раннер GitLab CI.
- Временная ручная CI-джоба (техника `[[temporary-ci-debug-job-technique]]`, ветка `tmp/debug-langfuse-logs`, удалена после использования) должна была прочитать `docker logs` контейнера и Langfuse-трейсы напрямую через `docker exec`.
- Джоба провисела в статусе Pending 8+ минут без раннера. Параллельно обычный merge-пайплайн (`#876`, не связанный с этим тестом) тоже завис в состоянии Running на том же отрезке времени.
- Вывод: проблема не в самом Python-процессе бота, а во всём dev-хосте целиком (сеть, ресурсы или сам упавший `gitlab-runner`) — три независимых сигнала (бот, чужой pipeline, наша debug-джоба) зависли одновременно.
- Не удалось починить/перезапустить самостоятельно — оставлено пользователю/DevOps.

**Итог по загрузке**: 4 накладные так и не были отправлены (прогон остановлен по решению пользователя), плюс накладная a4b8fe44 (получившая psycopg2-ошибку) реально не дошла до ИИ.

## Данные из Langfuse (авторитетный источник, не Telegram-чат)

Проверено через веб-UI Langfuse Cloud (`Autosnab` проект, вкладка Tracing, фильтр «Past 1 day»), не через CLI — ключи лежат только в `ENV_DEV` GitLab (нет локально, SSH к серверу тоже нет).

- **18 трейсов `parse-invoice`**, все уровня `DEFAULT` (ни одного `ERROR` — то есть сама OpenAI-часть пайплайна не бросала исключений; и psycopg2-ошибка, и зависание бота происходят вне трассируемого спана).
- Модель `gpt-5-mini`, суммарно **$0.081348**, **151.95K токенов**.
- Медианная латентность ~15–18с на накладную — стабильно.
- **18 трейсов = ровно 18 успешно финализированных накладных** (сходится с ручным подсчётом по Telegram: 24 файла − 1 отклонённая до OCR (№459) − 1 потерянная на psycopg2-ошибке (a4b8fe44) − 4 неотправленные = 18).

### Реальный «дрейф цифр» — живое воспроизведение проблемы из `lilia-feedback-2026-07-17-parsing-instability.md`

Накладная №21 (`acef2581`, 23:23) и самая первая накладная сессии (`0b6f262c`, 22:16) — **один и тот же исходный документ** (Поставщик «ЛИР ООО», № ТТН `9610429080689`, повторно сфотографированный/загруженный). Итоговые суммы разошлись:

- 22:16: `total_with_vat` не зафиксирован дословно в чате как отдельное поле, бот показал «Сумма: 31597.81»
- 23:23: `total_without_vat: 31080.98`, `total_with_vat: 35416.02`

Разница ~12% на одном и том же документе при независимом распознавании — то есть неопределённость модели на одних и тех же пикселях, ровно то, что описывала Lilia 2026-07-17 (Issue 1, "quantity digit drift"), только теперь с полным Langfuse-трейсом обеих попыток для сравнения бок о бок.

## Прочие находки за прогон

- **1 полный отказ до OCR**: накладная №459 (двухстраничная) — автоопределение ориентации страницы 1 вернуло уверенность 0.3 (порог не пройден), изображение не передано на распознавание вообще. Реальный дефект качества съёмки (фото повёрнуто), не баг кода — но подтверждает ценность идеи из §5 `telegram-bot-ux-hardening-plan.md` («сообщите о низкой уверенности»), только на уровень раньше: сообщать о проблеме ориентации сразу при приёме фото, а не после отказа.
- **1 частичное распознавание**: накладная (`6a1cad20`) — в карточке результата только поле «Сумма», без Поставщика/Номера/Даты, без объяснения причины. Прямое совпадение с §5 плана (`telegram-bot-ux-hardening-plan.md`) — «уровень уверенности по каждому полю» решил бы именно это.
- **Дедупликация работает корректно**: минимум 6 накладных в прогоне помечены ботом «похож на уже загруженный» — как против вчерашней сессии, так и друг против друга внутри сегодняшнего набора (несколько файлов в исходной папке — фотографии одних и тех же бумажных накладных, снятые повторно).
- **Сырая ошибка БД утекла прямо пользователю** (см. блок про сбой выше) — прямое живое подтверждение §2 плана (`telegram-bot-ux-hardening-plan.md`, «маскирование сырых ошибок») — приоритет 1 там не случаен.
- **`/done` не работает** (см. раздел «Механика загрузки») — это функциональный баг, а не просто пункт UX-плана; стоит завести отдельно от `telegram-bot-ux-hardening-plan.md`, так как ломает документированную самим ботом альтернативную команду, а не просто неидеальный тон сообщений.

## Что не сделано

- Не собран полный financial reconciliation по Google Sheets (таблица `Копия АвтоСнаб Кафе Ромашка`) — вкладка `1 Накладная` оказалась «текущий черновик на проверке», перезаписывается каждой новой накладной (в т.ч. чужими, не связанными с этим тестом, параллельными загрузками), поэтому не годится как источник истории; вкладка `Загрузка тест` содержит только старые (17.06.2026) строки, не связанные с этим прогоном. Историю по всем 18 обработанным документам восстанавливать оттуда не пытались — Langfuse оказался более надёжным источником для статистики самого пайплайна распознавания, но не для проверки итоговой записи в целевую таблицу.
- 4 накладные (`c03d1d9b`, `ed62cc11`, `f912b24a`, `fb6a1400`) не отправлены из-за сбоя dev-хоста.
- Причина самого сбоя dev-хоста не диагностирована до конца (нет SSH, debug-CI-джоба не дождалась раннера) — открытый вопрос для DevOps/пользователя.

## Рекомендации по правкам кода (приоритизация)

1. Реализовать §2 `telegram-bot-ux-hardening-plan.md` (маскирование сырых ошибок) — этот прогон дал конкретный живой пример вместо гипотетического
2. Починить или убрать `/done` как задокументированную команду — либо реализовать обработчик, либо убрать из текста бота и вики, чтобы не расходиться с реальным поведением
3. Cross-check итоговой суммы документа против суммы по строкам при распознавании (уже отмечено как открытый Phase 5 в `invoice-recognition-hardening-plan.md`) — прямое противоядие найденному 12%-дрейфу
4. §5 `telegram-bot-ux-hardening-plan.md` (уровень уверенности по полю) — снимет и частичное распознавание (`6a1cad20`), и молчаливый отказ по ориентации (№459)
5. Мониторинг/алертинг на недоступность БД и на зависание самого процесса бота — 20+ минут простоя без автовосстановления и без алерта прошли незамеченными до ручной проверки
