ОТЧЁТ ДЛЯ ТИМЛИДА
Проект: autosnab_mvp
Дата: 2026-07-20

Что реализовано в проекте и как оно работает.


1. ОБЩАЯ АРХИТЕКТУРА

Проект — конвейер обработки первичных документов (накладные, УПД, чеки):
изображение/PDF -> извлечение текста -> структурирование через ИИ ->
детерминированная нормализация -> сопоставление со справочниками ->
запись в общую Google-таблицу.

Источники загрузки — два: веб-страница загрузки в самом бэкенде и
Telegram-бот. Оба идут через один и тот же серверный пайплайн, бизнес-логика
не дублируется ни в UI, ни в боте.


2. РАСПОЗНАВАНИЕ ДОКУМЕНТОВ (МУЛЬТИ-ПРОВАЙДЕРНАЯ СХЕМА)

Реализованы и работают три источника "сырого" текста документа:
  - прямое чтение текстового слоя PDF (для PDF с текстом, без OCR);
  - Google Drive OCR — основной провайдер для фото/сканов;
  - MinerU — локальный OCR/layout-движок (работает офлайн, без внешних
    API), используется как резервный провайдер, когда Google OCR не
    вернул текст.

Логика выбора провайдера зашита в бэкенде и не настраивается ботом/UI —
оператор просто загружает файл, система сама решает, чем его читать.


3. КАК РАБОТАЕТ OPENAI В ПАЙПЛАЙНЕ

Роль модели: OpenAI — единственный слой, который структурирует "сырые"
данные документа (текст OCR/MinerU + сами картинки страниц) в финальный
набор полей накладной. Модель не имеет доступа к Google Sheets, не выбирает
колонки, не назначает бизнес-статусы напрямую и не выполняет расчёты —
только извлекает и предлагает кандидатов значений. Все итоговые решения
(нормализация, валидация, статусы, запись) принимает детерминированный код
бэкенда уже после ответа модели.

Технически вызов реализован так:
  - используется Responses API (`client.responses.parse`), модель по
    умолчанию — `gpt-5-mini`;
  - ответ модели строго типизирован через Structured Outputs: заранее
    описанная Pydantic-схема (`InvoiceParserResult`) гарантирует, что модель
    вернёт JSON нужной формы, а не произвольный текст;
  - запрос мультимодальный: в один вызов передаются одновременно
    (а) распознанный OCR/MinerU-текст как `input_text` и (б) сами
    изображения страниц документа как `input_image` (в base64, с высокой
    детализацией), до 12 страниц на документ. Это значит, что модель может
    "подсмотреть" значение прямо в фото, даже если OCR его исказил или
    пропустил;
  - системный промпт задаёт модели предметные правила распознавания
    российских первичных документов: брать номер документа только из
    реквизита номера (не из артикула/штрихкода), не склеивать соседние
    товарные строки, сохранять повторяющиеся строки чека отдельно и по
    порядку, не придумывать отсутствующие значения;
  - отдельно, для каждой товарной строки, промпт требует структурный разбор
    названия: чистое название без служебных слов и кодов, бренд/сорт/вкус,
    данные фасовки (вес/объём/размер упаковки), единицы и количество из
    документа, количество единиц в упаковке, извлечённые внутренние коды и
    кандидата коэффициента для последующего пересчёта в учётные единицы.
    В промпте зафиксированы конкретные примеры разбора (например, «0,5Л
    12ШТ» -> множитель 6, единица учёта «л»);
  - если модель не уверена в товаре, фасовке или единице, она обязана
    выставить `needs_review=true`, снизить `confidence` и кратко объяснить
    причину — это поле дальше используется бэкендом для маркировки строки
    на проверку;
  - модель также обязана расставлять `review_flags` для неоднозначных,
    нечитаемых или отсутствующих значений и для расхождений итоговых сумм —
    это отдельный сигнал, независимый от построчного `needs_review`.

Что происходит с ответом модели: он проходит через детерминированную
нормализацию (см. раздел про валидацию) — даты, ИНН, форма документа,
дедупликация, обязательные поля, пересчёт единиц — и только после этого
превращается в строки, которые могут попасть в Google-таблицу. Каждый вызов
модели полностью логируется в отдельный debug-трейс (сохранённые запрос и
ответ), что позволяет разбирать конкретные случаи распознавания постфактум.

Если предварительный текстовый/визуальный evidence оказался полностью
пустым (все OCR-провайдеры не вернули текст и нет изображений), вызов
OpenAI не выполняется — пайплайн останавливается раньше, чтобы не тратить
запрос на заведомо пустой документ.


4. МНОГОСТРАНИЧНЫЕ ДОКУМЕНТЫ

Один документ может состоять из нескольких файлов/фото (например, 2 страницы
товарной накладной). Реализовано:
  - логический ID документа, отдельный от ID отдельных файлов/страниц;
  - объединение доказательств (evidence) со всех страниц в один запрос к
    модели;
  - сохранение порядка страниц и исходных имён файлов;
  - один документ = один блок в таблице, а не несколько разрозненных записей.

В веб-интерфейсе загрузки страницы можно менять местами и удалять до
отправки. В Telegram-боте документ собирается пошагово: каждая следующая
присланная страница добавляется к тому же черновику, завершение — по кнопке.


5. ДЕТЕРМИНИРОВАННАЯ ВАЛИДАЦИЯ И НОРМАЛИЗАЦИЯ ПОСЛЕ МОДЕЛИ

ИИ-модель только извлекает кандидатов значений — окончательные бизнес-решения
(статусы, распределение по колонкам, авторизация записи) принимает
детерминированный код бэкенда:
  - нормализация дат, сумм, НДС;
  - очистка и валидация ИНН, включая обнаружение слипшихся ИНН/КПП;
  - каноникализация формы документа (Торг-12, УПД, Кассовый чек и т.д.)
    строго под реальный выпадающий список Google-таблицы;
  - обнаружение дублей загруженных документов, включая нормализацию разных
    написаний номера накладной;
  - обязательная маркировка "Требует проверки" при отсутствии ключевых полей
    (поставщик, номер документа, дата, ИНН) — документ с пустыми
    обязательными полями не может тихо уйти в таблицу как "готовый";
  - пустой результат от провайдеров или от модели останавливает пайплайн до
    сохранения — в таблицу никогда не попадает пустая заготовка документа.


6. СОПОСТАВЛЕНИЕ С ТОВАРНЫМ СПРАВОЧНИКОМ

Реализован отдельный слой нормализации товарных позиций:
  - очистка и нормализация наименования товара;
  - извлечение и проверка данных об упаковке (количество в упаковке,
    единицы измерения);
  - конвертация количества/цены между единицами документа и учётными
    единицами;
  - сопоставление с товарным справочником и справочником фасовок из
    Google-таблицы, включая локальный SQLite-кэш этих справочников с
    нечётким (fuzzy) поиском для офлайн-сопоставления;
  - для товара, не найденного в справочнике, наименование всё равно всегда
    заполняется нормализованным вариантом (никогда не остаётся пустым),
    а строка получает корректный статус "Нет в справочнике"/"Сопоставление".


7. ЗАПИСЬ В GOOGLE-ТАБЛИЦУ

Реализован прямой построитель канонических строк листа "Накладная" — запись
идёт строго под текущий реальный контракт колонок боевой таблицы (43 колонки,
имена и порядок сверены напрямую с production-таблицей через Google Sheets
API, включая недавно добавленные колонки "Код товара УС" и "ID строки").

Соблюдаются бизнес-правила таблицы:
  - статус документа выставляется только в первой строке блока документа;
  - "Корректировка" остаётся построчной (не документо-уровневой);
  - новые блоки документов вставляются сверху с разделительной пустой
    строкой между документами;
  - диапазон записи в Google Sheets рассчитывается по фактической ширине
    строки, а не зашит константой.

Запись выполняется через официальный OAuth-доступ (учётные данные и токены
хранятся только в переменных окружения, не в файлах в репозитории).


8. TELEGRAM-БОТ

Бот полностью реализован и подтверждён рабочим на реальных загрузках
(подтверждено сквозным тестом: реальное фото накладной УТ-35634 дошло от
Telegram до записи в Google-таблицу).

Возможности бота:
  - приём фото/PDF документа, в том числе многостраничного (несколько фото —
    один документ, подтверждение кнопкой "Готово"/"Продолжить");
  - постоянная reply-клавиатура с основными действиями;
  - отправка промежуточных статусных сообщений по мере прохождения этапов
    обработки (принят в обработку -> извлекаем данные -> обрабатываем через
    ИИ -> загружаем в таблицу) — оператор видит прогресс, а не тишину;
  - команда статуса — показывает последний обработанный документ, если
    активного черновика нет;
  - команда сброса черновика;
  - в финальном ответе бот отдаёт короткую сводку по документу и прямую
    ссылку на Google-таблицу.

Архитектурно бот — тонкий адаптер: вся бизнес-логика (OCR, ИИ-парсинг,
нормализация, запись в таблицу, дедупликация) выполняется бэкендом, n8n
только маршрутизирует сообщения Telegram и не хранит состояние сессии сам —
всё состояние черновика документа хранится на сервере.


9. BACKEND API ДЛЯ БОТА

Отдельный набор эндпоинтов под префиксом `/api/v1/invoice-review/bot/*`
реализован и закрыт общим секретным ключом (`X-Bot-Api-Key`):
  - постраничная загрузка в черновик документа;
  - статус текущего черновика;
  - сброс черновика;
  - завершение черновика и запуск обработки;
  - получение последнего обработанного документа по чату.

Все загрузки от бота фиксируются в отдельном постоянном журнале
(`ingestion_uploads`): кто загрузил, откуда, путь к файлу, статус, текст
ошибки — по каждой загрузке можно восстановить полную историю.


10. ВЕБ-ИНТЕРФЕЙС ЗАГРУЗКИ

Отдельная страница загрузки в самом бэкенде поддерживает:
  - выбор метода распознавания на уровне документа (Google OCR / MinerU /
    гибридный режим), независимо от глобальной настройки;
  - предпросмотр загружаемых изображений/PDF прямо на странице;
  - встроенную авторизацию Google (статус, кнопка авторизации во всплывающем
    окне) без ухода со страницы;
  - постраничный (по этапам пайплайна) вывод логов обработки в реальном
    времени по каждой загрузке — оператор видит, на каком этапе находится
    документ.


11. ИНТЕГРАЦИЯ С IIKO

Реализовано автозаполнение полей под учётную систему iiko (сопоставление
позиций с внутренним справочником) и предпросмотр/экспорт входящей накладной
в формате XML iiko.


12. РАЗВЁРТЫВАНИЕ

  - Единая сборка через Docker Compose: backend, персистентные тома для
    SQLite, загрузок, экспортов и кэша моделей MinerU.
  - Публикация бэкенда наружу — два рабочих профиля: временный туннель
    (ngrok) для локальной разработки и постоянный вариант через Caddy с
    автоматическим бесплатным HTTPS-сертификатом (Let's Encrypt) на базе
    nip.io — без необходимости покупать домен.
  - Бэкенд реально развёрнут и работает на выделенном VPS пользователя,
    отвечает по HTTPS с доверенным сертификатом, проверен внешними запросами
    (не с самого сервера).
  - Настроено ограничение памяти контейнера бэкенда для работы на
    небольших/разделяемых VPS.
  - Настроена проверка готовности БД при старте контейнера
    (`/health/runtime`), задействована в Docker healthcheck.


13. ТЕСТИРОВАНИЕ

Функциональность покрыта автотестами на уровне сервисов: извлечение
документов, OCR-провайдеры, нормализация счетов, построение строк для
Google-таблицы, обработка черновиков бота. Отдельно ведётся набор из
реальных фото-документов (golden set) для регрессионного сравнения
результатов распознавания с ожидаемыми значениями.
